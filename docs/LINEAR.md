# Linear 사용 규칙

작업 관리는 Linear로 한다. 사람과 Claude가 같은 규칙을 따른다.
Claude는 Linear 이슈를 만들거나 고칠 때, 이슈 작업을 시작할 때, PR을 열 때 이 문서를 먼저 읽는다.

## 기본 정보

- 팀: `Programmers-05`, 이슈 키 `PRO` (예: `PRO-12`)
- 프로젝트: `크루런` (이 레포의 Linear 프로젝트)
- 상태: Backlog → Todo → In Progress → In Review(PR 열림) → Done (안 할 일은 Canceled, 중복은 Duplicate)
- 라벨: `Feature`(새 기능), `Bug`(고장), `Improvement`(기존 기능 개선) 중 하나
- Claude는 레포 루트의 `.mcp.json`으로 Linear에 연결된다. 처음 한 번 각자 인증한다.

## 일정과 사이클

프로젝트 하나를 두 분기로 나눠 진행한다. 분기는 마일스톤으로, 주 단위 할 일은 사이클로 관리한다.

| 마일스톤  | 날짜                      |
| --------- | ------------------------- |
| 세미 제출 | 2026-10-22(목)            |
| 세미 발표 | 2026-10-23(금)            |
| 최종 발표 | 2026-11-23(월)            |

사이클은 **1주, 목요일 시작, 수요일 끝**이다. 세미 분기는 사이클 하나가 단계 하나다.

| 사이클 | 기간          | 단계      | 수요일 점검                  |
| ------ | ------------- | --------- | ---------------------------- |
| 1      | 10/1 ~ 10/7   | 기획      | 개발할 이슈가 다 쪼개져 있다 |
| 2      | 10/8 ~ 10/14  | 개발      | Feature 이슈가 다 Done이다   |
| 3      | 10/15 ~ 10/21 | 테스트    | Bug 이슈가 다 닫혀 있다      |
| 4      | 10/22 ~ 10/28 | 제출·발표 | 세미 제출·발표를 마쳤다      |

최종 분기는 사이클 5(10/29)부터 8(11/19 ~ 11/25)까지다. 최종 발표는 사이클 8 안에 있다.

- **수요일 점검**: 끝내지 못한 이슈는 다음 사이클로 자동으로 넘어간다. 넘어간 이슈가 많으면 다음 사이클 범위를 줄인다.
- **이슈 넣기**: 새 이슈는 Backlog에 두고, 수요일 점검 때 다음 사이클에 넣을지 정한다. 급한 Bug만 바로 현재 사이클에 넣는다.

## 처음 설정 (사람)

1. Linear 초대를 수락한다.
2. Claude Code에서 Linear 연결을 인증한다. 터미널이면 `claude` 실행 후 `/mcp`, 데스크톱 앱이면 커넥터 설정에서 Linear를 연결한다.
3. 단축키 세 개만 먼저 익힌다: `C` 새 이슈, `Cmd+K` 명령창, `/` 검색.

## 이슈 쓰기

이슈 하나 = 하루 이틀 안에 끝나는 일 하나. 더 크면 하위 이슈로 쪼갠다.

- **제목**: 무엇을 하는지 한 줄. "~하기"로 끝낸다. 예: `크루 초대 수락 화면 만들기`
- **본문**: 아래 세 칸을 채운다.

  ```md
  ## 배경
  왜 필요한지 해요체로 써요. 관련 정책·화면 링크

  ## 할 일
  - 구체적인 작업 (예: 초대 수락 API 연결하기)

  ## 완료 기준
  - [ ] 확인할 수 있는 조건 (예: 초대 링크로 들어오면 수락 버튼 보임)
  ```

- **본문 문체**: 할 일·완료 기준 같은 항목은 명사형(`~하기`, `~함`, `~ 보임`)으로 끝낸다.
  배경처럼 설명이 필요한 문장은 해요체(`~나와요`, `~없어요`)로 쓴다. `~한다`, `~있다` 같은 평서체는 쓰지 않는다.

- **필수 항목**: 라벨 1개, 우선순위, 프로젝트. 사이클이 켜져 있으면 이번 사이클에 넣을지 정한다.
- **링크만 붙인다**: 정책·기획·디자인 원본(Figma, `docs/`)은 링크로 연결한다. 내용을 이슈에 복사하면 원본과 어긋난다.

## 작업 흐름

1. **시작**: 이슈를 나에게 배정하고 In Progress로 옮긴다. Claude로 작업하면 아래 "작업 시작 체크"를 Claude가 한다.
   PR을 열 때 아직 Backlog·Todo면 `linear-sync`가 한 번 더 In Progress로 옮긴다.
2. **브랜치**: `<type>/PRO-<번호>-<짧은-설명>`. type은 커밋과 같은 Conventional Commits 종류다. 예: `feat/PRO-12-crew-invite-accept`
   이슈에서 `Cmd+Shift+.`로 브랜치 이름을 복사할 수 있지만, 앞의 `<type>/`은 직접 붙인다.
3. **PR**: 제목은 커밋 규칙을 따르고, 본문에 `Closes PRO-12`를 넣는다.
   본문은 `.github/pull_request_template.md`의 6개 섹션(배경·의도·구현·중점 리뷰 사항·확인 방법·기타)을 채운다. CI `pr-body`가 섹션 제목이 다 있는지 검사한다.
4. **끝**: PR이 머지되면 연결된 이슈가 Done으로 옮겨진다. PR이 없는 일(기획, 디자인)은 결과물 링크를 댓글로 남기고 직접 Done으로 바꾼다.

### PR 자동 연결 (`linear-sync` 워크플로)

Linear 공식 GitHub 연동이 동작하지 않아, `linear-sync.yml`이 Linear API로 이슈를 직접 갱신한다.
브랜치 이름, PR 제목·본문에 있는 `PRO-<번호>`로 이미 있는 이슈를 찾는다. 이슈를 새로 만들지는 않는다.

| PR 상황 | 하는 일 |
| --- | --- |
| PR 열림, 본문 수정, 초안 해제 | 이슈에 PR 링크를 붙이고, Backlog·Todo 이슈를 In Progress로 옮긴다 (초안 PR은 링크만) |
| 머지됨 | 브랜치 이름·제목에 있는 이슈와 본문에 `Closes PRO-12`로 적은 이슈를 Done으로 옮긴다 |
| 머지 없이 닫힘 | 아무것도 바꾸지 않는다 |

- Done으로 옮기지 않고 연결만 하려면 브랜치·제목에서 번호를 빼고 본문에 `Refs PRO-12`로 쓴다.
- 팀원마다 자기 Linear 개인 API 키를 저장소 시크릿 `LINEAR_API_KEY_<GitHub 아이디>`로 등록한다. 방법은 [LINEAR-API-KEY.md](LINEAR-API-KEY.md).
  이벤트를 일으킨 사람(머지한 사람 등)의 키를 쓰고, 없으면 PR 작성자 키를 쓴다. 둘 다 없으면 아무것도 하지 않고 넘어간다.
  Linear에는 그 키 주인이 바꾼 것으로 기록된다.
- 워크플로는 PR의 base 브랜치와 상관없이 **기본 브랜치(main)에 있는 파일로만** 돈다(`pull_request_target`, GitHub 2025-12 변경).
  main에 이 워크플로·스크립트가 없으면 dev로 가는 PR에서도 아예 실행되지 않는다. 고친 내용은 main에 들어가야 반영된다.
- 실행 기록은 PR의 Checks 탭 `linear-sync`에서 본다. 이슈 갱신에 실패하면 이 체크가 빨간색이 된다(머지는 막지 않는다).

## GitHub 활용

할 일의 원본은 Linear 하나다. **GitHub 이슈는 쓰지 않는다**(양쪽에 적으면 금방 어긋난다). GitHub에서는 PR·CI·마일스톤만 쓴다.
Wiki와 Projects 탭은 팀 작업용이 아니라 외부 공개용이다. Projects는 프로젝트 진행 상황을, Wiki는 팀 규칙(브랜치·커밋·코드 컨벤션)을 밖에서 볼 수 있게 보여 준다.

### main에 머지하려면 (브랜치 보호)

main에는 직접 푸시할 수 없고 PR로만 들어간다. 팀원 1명의 승인을 받고 아래 필수 체크가 모두 통과해야 머지 버튼이 열린다.
저장소 관리자는 PR에서만 이 조건을 건너뛰고 머지할 수 있다(main 직접 푸시는 관리자도 막힌다).

| 필수 체크 | 워크플로 | 검사 내용 |
| --- | --- | --- |
| `backend` | `backend-ci.yml` | `./gradlew build` (backend/ 변경이 없으면 건너뛰고 통과) |
| `frontend` | `frontend-ci.yml` | lint, format, typecheck, test, build (frontend/ 변경이 없으면 건너뛰고 통과) |
| `pr-title` | `pr-rules.yml` | PR 제목이 커밋 규칙(commitlint)에 맞는지 |
| `pr-branch` | `pr-rules.yml` | 브랜치 이름이 `<type>/PRO-<번호>-<짧은-설명>`인지 |

- Linear 이슈가 없는 작업(설정 정리 등)은 PR에 `no-issue` 라벨을 붙이면 브랜치 이름 검사를 건너뛴다.
- 제목 설명을 영어 대문자로 시작하면 commitlint가 막는다(`subject-case`). `ci: GitHub 설정 추가` ✗ → `ci: 저장소 설정 추가` ✓
- 필수 체크 이름은 job 이름이다. job 이름을 바꾸면 브랜치 보호 규칙도 같이 바꾼다.

### 마일스톤

GitHub 마일스톤은 Linear 마일스톤과 같은 이름·날짜로 둔다: 세미 제출(10/22), 세미 발표(10/23), 최종 발표(11/23).
`pr-milestone.yml`이 머지된 PR에 **머지 날짜(한국 시간) 이후로 마감이 가장 가까운 마일스톤**을 자동으로 붙인다. 직접 붙여 둔 PR은 건드리지 않는다.

## Claude 작업 규칙

- **만들기 전에 찾는다**: 이슈를 만들기 전에 같은 내용의 이슈가 있는지 검색한다. 있으면 그 이슈에 댓글로 더한다.
- **보여주고 만든다**: Linear는 팀 전체가 보는 곳이다. 이슈 생성·상태 변경·댓글은 초안을 사용자에게 보여주고 확인받은 뒤 실행한다. 여러 개면 한 번에 묶어서 확인받는다.
- **마일스톤을 붙인다**: 이슈는 `크루런` 프로젝트에 넣고, 끝나야 하는 마일스톤(세미 제출 / 최종 발표 등)을 붙인다. 어느 쪽인지 분명하지 않으면 사용자에게 묻는다.
- **이슈 번호를 이어 붙인다**: 사용자가 이슈 번호를 주면 브랜치 이름과 PR 본문에 그 번호를 넣는다.

### 작업 시작 체크

코드·문서를 고치는 작업을 시작할 때, 첫 수정 전에 한 번 한다. 질문에 답만 하는 일에는 하지 않는다.

1. **이슈 번호 찾기**: 사용자가 말한 `PRO-<번호>`, 없으면 현재 브랜치 이름(`git branch --show-current`)에서 찾는다.
   둘 다 없으면 Linear에서 비슷한 이슈를 검색해 후보를 보여 주고, 없으면 새 이슈 초안을 제안한다.
2. **이슈 조회**: Linear MCP로 상태·담당자·사이클·마일스톤을 읽는다.
   Linear MCP가 연결되어 있지 않으면 "Linear 연결이 없어 이슈 상태를 맞추지 못했다"고 알리고 작업은 계속한다.
3. **어긋난 것 고치기**: 아래 표에서 걸리는 것을 한 번에 묶어 한 줄로 확인받고 고친다.

| 조회 결과 | 고칠 내용 |
| --- | --- |
| 상태가 Backlog·Todo | In Progress로 옮긴다 |
| 상태가 Done·Canceled | 고치지 않고, 다시 열지 새 이슈로 할지 묻는다 |
| 담당자가 비어 있음 | 사용자에게 배정한다 |
| 담당자가 다른 사람 | 고치지 않고 알린다 |
| 사이클이 비어 있음 | 지금 사이클에 넣는다 |
| 마일스톤이 비어 있음 | 세미 제출 / 최종 발표 중 어느 쪽인지 묻는다 |

- 이미 맞으면 아무것도 묻지 않고 한 줄로만 알린다. 예: `PRO-12 In Progress · 이번 사이클 확인`
- 사용자가 "Linear 맞춰줘"처럼 여러 이슈를 맞춰 달라고 하면 같은 표로 이슈마다 점검한다.
  PR이 머지됐는데 Done이 아니면 Done으로, PR이 열려 있는데 Backlog·Todo면 In Review로 옮기는 것도 함께 제안한다.

## 진행 상황 공유

프로젝트 업데이트는 주 1회 쓴다. 형식:

```md
**상태**: 순조로움 / 주의 / 위험
**이번 주 한 일**: 머지된 PR, 끝난 이슈
**다음 주 할 일**:
**막힌 점**: 없으면 "없음"
```
